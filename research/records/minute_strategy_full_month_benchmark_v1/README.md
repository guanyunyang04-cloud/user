# Full-month minute-strategy benchmark

This is the first full-universe throughput and memory-curve measurement after
the CPU/data-flow changes. It is an engineering benchmark of the current
causal rule runner, not a profitability conclusion.

## Run

- Target: all point-in-time main-board symbols in April 2022.
- Trading dates: 19.
- Symbols: 3,010 in the month-level universe (2,990--2,996 per date).
- DuckDB threads: 4.
- Signal and history symbol chunk: 128.
- Six MA periods: 10, 20, 40, 60, 120, 240.
- Normalized `events`, `paths`, and `references` artifacts enabled.
- Hard machine reserve: 0.5 GiB; an external 0.75 GiB abort threshold was used
  as an additional early-warning guard.

## Result

The run completed successfully in 7,005.635 wall-clock seconds (116.8 min;
6,621.904 seconds in the runner's month timer). It produced 6,091,670 outcome
rows and 19 complete date partitions. The normalized output contains the same
6,091,670 events, 2,524,171 unique forward paths, and 6,091,670 references.

The one-second telemetry curve recorded 6,932 samples:

- minimum available system memory: 3.552 GiB;
- median available memory: 5.314 GiB;
- 1st percentile available memory: 4.555 GiB;
- peak process-tree RSS: 3.399 GiB;
- no external abort and no hard-floor breach.

The complete raw curve and runner log are retained in the local ignored paths
`tmp/perf_full_month_2022_04_t4_c128_v2/memory_curve.jsonl` and
`tmp/perf_full_month_2022_04_t4_c128_v2/runner.log`. The generated study output
is under the ignored local path
`runs/minute_ma_month_2022_04_t4_c128_v2/`.

## Scaling fix validated by this run

The first attempt with four threads failed inside DuckDB while aggregating the
full historical minute window: the all-universe query's final global sort and
group state exceeded its internal memory limit, even though system memory was
still above the 0.5 GiB reserve. The history loader now removes that redundant
SQL sort and aggregates symbols in bounded chunks, then performs one small
hourly-frame sort in pandas. A 128-symbol chunked history result matched the
unchunked result exactly on a controlled comparison, and the full-month run
completed without an OOM.

The older April output was generated by an earlier strategy-registry revision,
so its total row count is not a valid parity target. A same-source one-date
`2-thread/512-symbol` replay matched the new `4-thread/128-symbol` output on
all 70 output columns for all 393,275 rows (including strategy counts, signal
keys, entry fields, and every stored forward metric).

## Decision

`4 threads + 128 symbols` is safe for this full-month workload on the current
machine when the bounded history path is used. It is a measured starting point,
not a promise for every month or concurrent workload. Date-level parallelism
remains opt-in: use the parent-side admission helper and re-check available
memory before launching each worker. Do not start the three-year run until a
few more representative months have been measured.
